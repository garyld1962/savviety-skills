# Gamma Brief
## Copilot-native executive deck for engineering leadership

Use this document as the direct source for a Gamma deck aimed at leadership.

The goal is to explain the **Copilot-native workspace** as an **engineering
operating model**, not just a set of AI prompts. The deck should make clear
that this approach goes **beyond code generation** into requirements shaping,
delivery governance, review quality, investigation, and organizational learning.

---

## What Gamma should produce

- **Audience:** CTOs, VPs of Engineering, Directors of Engineering, Heads of Platform, senior product/engineering leaders
- **Tone:** executive, credible, practical, strategic
- **Style:** leadership architecture deck, not a product demo
- **Deck length:** 10-12 slides
- **Visual bias:** operating model diagrams, lifecycle maps, business outcome tables, governance overlays
- **Avoid:** prompt catalogs, feature-tour slides, generic AI hype, consumer-product language, or claims that imply full autonomy without controls

---

## Core message

This system is **not** primarily about generating code faster.

It is about creating a more reliable engineering system that helps teams:

1. **Shape requirements before coding starts**
2. **Move from plan to delivery with clearer governance**
3. **Apply repeatable review standards instead of ad-hoc judgment**
4. **Investigate systems with evidence, not intuition**
5. **Capture knowledge so learning survives the session and the individual**

The leadership story is:

- code generation is only one layer
- the higher-value opportunity is **standardizing engineering decision-making**
- the platform helps scale good engineering behavior, not just speed up typing

---

## Leadership framing

Position the Copilot-native workspace as an operating model with five layers:

1. **Built-ins** for planning, review, research, task management, diff/PR inspection, and context control
2. **Prompts** as workflow entry points for specific engineering jobs
3. **Agents** as bounded specialists for review, ideation, orchestration, and reporting
4. **Skills** as the reusable knowledge layer
5. **Instructions** as always-on governance and operating rules

This is important because it shows discipline:

- use the platform natively where possible
- customize only where the organization needs leverage
- keep durable logic out of one-off prompts

---

## What leadership should understand

This workspace covers more of the software lifecycle than code generation alone:

- **before implementation** — business shaping, PRD/AERS refinement, glossary and context capture
- **during implementation** — planning, execution, checkpoints, delivery coordination
- **after implementation** — review, adversarial challenge, postmortem, reusable lessons
- **outside implementation** — investigation, environment routing, migration guidance, dependency risk review

The key point for leaders:

**This is closer to an engineering workflow system than a coding assistant skin.**

### Slide 10 — Adoption model
**Title:** How leadership should think about rollout

**Content:**
- start with built-in Copilot features as the default layer
- add a small number of high-value custom flows first
- prioritize workflows with high ambiguity, high review cost, or high delivery risk
- keep the custom surface thin and maintainable
- treat reusable skills and instructions as the scaling mechanism

**Suggested visual:**
- Crawl / walk / run path:
  - built-ins first
  - targeted custom flows
  - governed multi-stage workflows

**Leadership takeaway:**
- Adopt this as a capability system, not a one-time prompt rollout
